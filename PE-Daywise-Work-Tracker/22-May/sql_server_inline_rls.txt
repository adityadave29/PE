SQL Server does not allow direct row-filter expressions inside CREATE SECURITY POLICY because its Row-Level Security architecture is designed around predicate functions, not inline policy clauses. Unlike PostgreSQL, where you can write logic directly in the policy using USING (condition), SQL Server requires every filter to be encapsulated in an inline table-valued function (TVF). The security policy itself acts only as a wrapper that tells SQL Server which function to call for each row; it does not contain the filtering logic. Microsoft designed it this way so the predicate can be compiled, schema-bound, reused, and integrated safely into the query optimizer as part of query execution. Because of this architecture, CREATE SECURITY POLICY accepts only ADD FILTER PREDICATE function_name(column) syntax and does not support writing normal conditions like WHERE, EXISTS, or joins directly inside the policy definition. In short, in SQL Server the policy is just a binder, while the actual access logic must always live inside a function.
